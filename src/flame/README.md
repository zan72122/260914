# src/flame — 物理ベースの手続き炎（M1）

『ほんとうの火』の炎。**色は発光波長から算出する**（PLAN.md §1 / §4）。
色をデザイナーが目で決めることはしない。決めるのは形と揺らぎだけ。

## ファイル

| ファイル | 役割 | 依存 |
|---|---|---|
| `spectra.ts` | 元素ごとの発光線（波長 nm・相対強度・発光種・出典メモ） | なし |
| `color.ts` | 発光線 → CIE 1931 XYZ → 線形 sRGB → 表示 sRGB、ガス炎との合成、輝度正規化 | `spectra.ts` のみ |
| `afterglow.ts` | 炎から出た後の余熱発光（約 3 秒） | なし |
| `flame.frag.glsl` / `flame.vert.glsl` | 手続き炎の WebGL シェーダ | なし |
| `FlameRenderer.ts` | 上のシェーダを PixiJS v8 の `Filter` として貼る薄いクラス | **PixiJS v8** |
| `index.ts` | 純粋な部分だけの入口（PixiJS を引き込まない） | — |
| `glsl.d.ts` | Vite の `?raw` インポート用の型宣言 | — |

`index.ts` は `FlameRenderer` を re-export しない。そのため PixiJS を import できない
環境（Node 上の Vitest など）でも `spectra` / `color` / `afterglow` をそのまま検査できる。

## 1. 色をどう算出しているか

```
発光線 [(λ, 強度), …]
  └─ 総放射パワーで正規化
  └─ CIE 1931 2° 等色関数で積分            → XYZ
       Y = 単位放射パワーあたりの視感効率（555 nm 単色で 1.0）
  └─ 色度 (x, y) を取り出す                → ここから先、色度は一切変えない
  └─ その色度で sRGB が出せる最も明るい色を作る
       ・XYZ → 線形 sRGB（D65, IEC 61966-2-1 の行列）
       ・色域外なら「同じ輝度の白へ真っ直ぐ寄せて」色域内に入れる
       ・最大成分が 1 になるよう規格化
  └─ 明るさだけを掛ける（輝度正規化。下記 §3）
  └─ sRGB 伝達関数                         → 表示 sRGB / HSV / #rrggbb
```

### 等色関数

**CIE 1931 2° 標準観測者の実表**を 380–780 nm / 5 nm 刻みで埋め込んでいる（81 点）。
値は CIE 公表の 1 nm 表（`colour-science/colour` の
`colour/colorimetry/datasets/cmfs.py`, "CIE 1931 2 Degree Standard Observer"）から抜き出した。
間は線形補間。

解析近似（Wyman–Sloan–Shirley, JCGT 2013 の多ローブ・ガウス近似）は**採用しなかった**。
650–700 nm の裾で ȳ の相対誤差が 40% を超え、リチウム 670.8 nm 単色の色度が
x = 0.69 と算出されてしまう（正しくは x ≈ 0.73）。本作の要は「二つの赤の区別」なので、
この誤差は許容できない。

### 色域マッピング

単色線はどれも sRGB 色域の外にある。色域内に入れる方法として、
**同じ輝度の白（D65）へ真っ直ぐ寄せる**方式を採った。
CIE xy 平面で「色度点 → 白色点」の直線上を動く操作なので、**主波長が変わらない**。
成分をクリップする一般的な方式は色相を曲げるので使っていない。
どれだけ寄せたかは `FlameColor.gamutDesaturation` で読める。

### 二つの赤の区別（PLAN §3.2 / §3.5 の核心）

| 指標 | ストロンチウム | リチウム | 差 | テストの下限 |
|---|---|---|---|---|
| 主波長 | 624.1 nm | 657.3 nm | **33.2 nm** | 20 nm |
| CIE xy 距離 | — | — | **0.057** | 0.040 |
| HSV 色相 | 346.7° | 343.2° | **3.5°** | 2.0° |
| HSV 明度 | 0.676 | 0.446 | **0.230** | 0.15 |
| 視感効率の比 | 0.1575 | 0.0338 | **4.66 倍** | 3.5 倍 |
| 表示輝度の比 | — | — | **2.4 倍** | 2.0 倍 |

色相角の差が 3.5° しかないのは**誤りではなく現実**である。
どちらも赤であり、目で並べても紛らわしい。だから PLAN §3.5 はプリズムを置いた。
一方で**主波長は 33 nm、明るさは 2.4 倍**違い、これは画面上ではっきり分かる。
「ストロンチウムは明るい緋、リチウムは暗い深紅」という見え方になる。

リチウムが暗いのは、670.8 nm での比視感度 V(λ) が 0.031 しかないためで、
色を暗くする補正を入れているのではない。

## 3. 近似と限界（意図的な乖離を含む）

「本物の色」を優先する。色相を見栄えのためにずらしていない。
以下が、そこから外れている点の全部である。

### 3.1 明るさの正規化（`color.ts`）

色度は触らず、**明るさだけ**を次の式で正規化する。

```
scale = MIN_DISPLAY_SCALE + (1 - MIN_DISPLAY_SCALE) * min(1, 視感効率 / REFERENCE_EFFICACY)
        MIN_DISPLAY_SCALE = 0.10,  REFERENCE_EFFICACY = 0.45,  LUMINANCE_EXPONENT = 1.0
```

- 視感効率に**比例**させる（`LUMINANCE_EXPONENT = 1.0`、圧縮なし）。元素間の明るさの差は物理そのまま。
- 0.45 を超える元素（ナトリウム）は 1.0 に飽和する。画面は太陽ではないので上限はどこかに要る。
- 0.10 の床を設ける。これが唯一の圧縮で、Sr : Li の比を 4.7 : 1 から 2.4 : 1 に緩める。
  床が無いとリチウムが暗すぎて「炎の色が変わった」ことが見えない。
- `LUMINANCE_EXPONENT` を 0.5 にすれば sqrt 圧縮になる。変えるならここだけ。

彩度は**落としていない**。落ちているのは sRGB 色域に入れるために避けられない分だけで、
その量は `gamutDesaturation`（銅 0.39 / Sr 0.22 / Li 0.41）として読める。

### 3.2 発光線データ（`spectra.ts`）

- **分子バンドを線に離散化している。** 炎色の実体の多くは原子線ではなく
  SrCl・SrOH・CuOH・CuCl・C2 Swan などの分子バンドで、本来は数 nm〜数十 nm の幅を持つ。
  ここでは代表波長の線に潰している。色度への影響は小さいが、
  **M3 のプリズム表示では線が細く見えすぎる**。プリズム側で幅を持たせること。
- **相対強度は炎温度に合わせて補正している。** NIST ASD の Relative Intensity は
  アーク・放電（数千〜1 万 K）での値で、炎（約 2000 K、信号炎でも約 2400 K）とは
  励起分布が違う。上準位の高い線は炎では桁違いに弱いので、Boltzmann 因子の見積もりに基づき
  Li 610.4 nm を 0.008、Sr I 460.7 nm を 0.03 などに落としてある。理由は各定義の直上に書いた。
  これは色相を好みで動かす操作ではなく、光源条件を炎に合わせる操作である。
- **銅の青緑には塩素供与体を前提している。** 裸の銅線だけなら CuOH の緑に寄る。
  PLAN §3.2 が「青緑・他に青の線群」と定めているので CuCl バンド（428–452 nm）を含めた。
  花火工房の試し燃やし台という舞台上、塩化物が同居しているという想定。
- 特定の実測スペクトルの複製ではない。「その元素の炎色として一般に観測される見え方」の再現。

### 3.3 余熱発光（`afterglow.ts`）— 承認済みの乖離

現実には材料を炎から出せば数十 ms で消える。運搬中に色を見せるために 3 秒残す
（PLAN §3.3 / §7 でユーザー承認済み）。乖離を最小にするため、

- **色相は炎の中とまったく同じ**（線形 sRGB を定数倍するだけ）。
- 明るさだけを単調に落とし、3.0 秒でちょうど 0 にする。半減期は約 0.98 秒。

### 3.4 その他

- 煤の輝点は 1700 K の**灰色体**として扱っている。実際の煤は短波長側の放射率がやや高く、
  実測はもう少し白っぽい。また可視域だけで正規化しているので、
  `luminousEfficacy` は「可視放射あたり」であり黒体全体の発光効率ではない。
- 観測条件（順応・周囲の明るさ・表示装置の実際のガンマと色域）は考慮していない。
  夕暮れの暗い画面で見る前提だが、順応の効果はモデル化していない。
- 炎の**自己吸収・光学的厚み**、炎の厚みによる色の変化は扱っていない。
- **実 GPU 上での見た目は未検証**（§6 参照）。

## 4. シェーダの uniform

`flame.frag.glsl`。**このシェーダは色を決めない。** 色はすべて uniform で受け取る。
色リテラルを書かないことは `tests/flame/shader.test.ts` が機械的に検査している。

| uniform | 型 | 意味 |
|---|---|---|
| `uTime` | `float` | 秒。**GameClock 由来**。壁時計・フレーム番号は使わない（PLAN §4）。同じ `uTime` なら常に同じ絵 |
| `uElementColor` | `vec3` | 元素単体の炎色（線形 sRGB）。`elementFlameColor(id).linear` |
| `uBaseColor` | `vec3` | 素の青いガス炎＝外炎の色。`baseFlameColor().linear` |
| `uInnerColor` | `vec3` | 内炎（還元炎）の色。`innerConeColor().linear` |
| `uSootColor` | `vec3` | 煤の輝点の色。`sootColor().linear` |
| `uMix` | `float` | 0 = 素の青いガス炎、1 = 元素色が支配。内炎は `uMix * 0.6` でしか染まらない（還元炎では励起が弱いため） |
| `uIntensity` | `float` | 炎全体の強さ。1 が基準 |
| `uResolution` | `vec2` | 炎矩形のピクセルサイズ。縦横比の補正に使う |
| `uSeed` | `float` | シナリオ既定 seed 由来の定数（PLAN §5.5） |

`flame.vert.glsl` は PixiJS v8 の Filter 規約（`aPosition` と
`uInputSize` / `uOutputFrame` / `uOutputTexture`）に従う。Pixi の `defaultFilterVert` と等価だが、
差し込み側が Pixi の内部 export に依存しなくて済むよう自前で持っている。

シェーダ内の合成は `mix(uBaseColor, uElementColor, uMix)` を**線形光**で行う。
これは二つの光を足す操作なので物理的に正しい。`color.ts` の `flameColor()` は
放射スペクトルを混ぜてから表示正規化をかけるので明るさの扱いだけが違い、
色相の差は全 `uMix` で 12° 以内（テストで担保）。端点（0 と 1）では完全に一致する。

### 炎の形

- **外炎**: 口の少し上で最も太く、上へ細って千切れる。`outerWidth(y)`。
- **内炎**: 口のすぐ上の小さく安定した円錐（予混合炎の還元帯）。`innerWidth(y)`、y < 0.42 のみ。
- **揺らぎ**: 4 オクターブの value noise（fbm）。ゆっくり傾く成分と縁を乱す成分の 2 つ。
  上へ行くほど大きく揺れ、根元は口に固定されてほぼ動かない。
- **煤・輝点**: 上部で疎らに立ち上がる粒。セルごとの hash で位置と有無を決める。

## 5. 差し込み手順

```ts
import { FlameRenderer } from './flame/FlameRenderer.js';

const flame = new FlameRenderer({
  width: 220,          // 炎矩形の幅 [px]
  height: 320,         // 高さ [px]
  resolution: 0.35,    // 低解像度 FBO（PLAN §7）。Pixi が自動で拡大合成する
  seed: scenarioSeed,  // PLAN §5.5
});

flame.view.position.set(benchX, burnerMouthY); // view の原点 = 底辺中央 = バーナーの口
stage.addChild(flame.view);

// 毎フレーム。dt は必ず GameClock 由来の秒。
gameClock.onUpdate((dtSeconds) => flame.update(dtSeconds));

// 材料が炎に入った / 出た
flame.setElement('copper');      // mixTarget 既定 0.92（ガス炎自身の発光が残るので 1.0 にしない）
flame.setElement(null);          // 素の青いガス炎に戻る
```

- `flame.update(dt)` の中で `uMix` が目標へ指数的に追従する（既定 6 /s ≒ 0.5 秒で 95%）。
  フレームレートに依らない形なので、`clock.step(16)` を刻んでも一括で進めても同じ結果になる。
- `flame.getMix()` / `flame.getElement()` は `__fire.dump('flame')`（PLAN §5.1）から読む想定。
- 縦横の切り替えでは `flame.resize(w, h)` を呼ぶ。
- `Filter.resolution` を 1 未満にすることが PLAN §7 の「解像度を落とした FBO に描いて拡大」に当たる。
  合成は `blendMode: 'add'`（炎は背景に光を足すもので、背景を隠すものではない）。

GLSL は `?raw` インポートで読み込む（Vite 標準）。型は `glsl.d.ts` が与える。
`vite.config` も `tsconfig` も触らなくてよい。

### PixiJS 無しで使う

`FlameRenderer` を経由せず色だけ使いたい場合（プリズムの縞、材料の余熱発光、テスト）:

```ts
import { elementFlameColor, flameColor, baseFlameColor } from './flame/color.js';
import { afterglowIntensity } from './flame/afterglow.js';
import { ELEMENT_SPECTRA } from './flame/spectra.js';
```

`index.ts` も同じく PixiJS を引き込まない。

## 6. 未検証範囲

- **実 GPU 上での見た目は未検証。** このマイルストーンでは WebGL コンテキストを
  一度も作っていない。シェーダのコンパイル、PixiJS v8 の Filter へのバインド、
  低解像度 FBO の拡大結果、実機 iOS Safari での性能はどれも確認していない。
  検査したのはシェーダの**契約**（uniform の宣言、色を作っていないこと、
  時間源が `uTime` だけであること）と、色算出の数値だけ。
- スクリーンショットによる「炎領域の平均色相が仕様範囲内」（PLAN §5.5）の検証は
  M0 の `__fire` 入口と Playwright が揃ってから行う。
- 分子バンドを線に潰した影響は、M3 のプリズム表示で改めて見直す必要がある。
- 混色（銅＋ストロンチウム＝紫）は v2 の範囲なので実装していないが、
  `blendSpectra()` は任意のスペクトル同士を混ぜられるのでそのまま使える。

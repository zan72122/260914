# 『ほんとうの火』 開発計画（v1）

状態: **v1 実装済み（M0〜M5）**。承認は 2026-09-15。実装の実態は docs/DEV.md、配信手順は docs/DEPLOY.md を参照。

## 0. 一行要約

花火工房の試し燃やし台で、正体不明の材料を炎に入れて色で見抜き、
そのまま指を離さず、困っている場所へ届けると世界が直る。
名前は「求める声」と「礼の声」としてだけ現れる。プリズムで炎を見ると元素ごとの縞が見える。

## 1. 決定事項（ユーザー回答）

| 項目 | 決定 |
|---|---|
| 配布 | Web / PWA（Safari「ホーム画面に追加」、GitHub Pages 配信） |
| 音声 | iOS 内蔵合成音声のみ（Web Speech API, ja-JP） |
| 炎 | 物理ベースの手続き炎（WebGL シェーダ。色は実際の発光波長から算出） |
| v1 範囲 | プリズムの縞（分光）を含む。鉱物の見た目・混色・5場面は v2 以降 |
| v1 元素 | 銅・ストロンチウム・リチウム（赤2種を最初から共存させる） |
| 炎の場所 | 花火工房の試し燃やし台（家庭で真似できない専門の場） |
| 進行・保存 | 保存なし。毎回同じ世界から始まり、終わりがない |
| 実装体制 | Fable 5.1 は統制・監督・レビュー。実装は Opus 5 subagent に委任 |

## 2. 絶対条件との対応

1. 紙芝居・カード・テロップ・説明文・クイズ無し → 文字は一切描かない。名前は状況内の発話のみ。
2. 次に何をするか画面で分かる → 困りは絵で見える（火花を出す切れた線、手を振る人、暗いランプ）。材料は台の上に転がっている。炎は燃えている。
3. 世界そのものが UI → ボタン・メニュー・HUD を置かない。開始画面も無く、起動即工房。
4. 一本指 → ドラッグのみ。指を離さない一筆書きで「炎に入れる → 運ぶ → 置く」が完結する。
5. プレイヤーの行為で関係が成立 → 色が出るのは子どもが炎に入れた瞬間。仕事が動くのは子どもが届けた瞬間。
6. 赤2種 → 深紅（リチウム）と緋（ストロンチウム）を同じ台で共存。仕事も材料も別。プリズムの縞で決定的に見分けられる。
7. 科学的に大きく偽らない → 銅は銅線としてそのまま。リチウムは「電池の材料」として電池工場の受け口へ送り、電池が出てくる。金属＝電池とは描かない。ストロンチウムは赤い信号炎（発煙筒）と赤花火の材料。
8. 色違いの同一ミニゲームにしない → 3つの仕事は全て異なる物理現象（電気が流れる／燃えて信号になる／電池で装置が動く）。
9. 何度も触りたくなる → 困りは直しても数十秒で別の困りが起きる。炎に入れるだけでも楽しい（触るだけの反応を厚くする）。

## 3. 世界と場面

### 3.1 舞台

夕暮れの港に建つ花火工房。画面は一枚の連続した世界。

- **手前（画面下 1/3）**: 試し燃やし台。ガスバーナー1本、金属の輪（材料をすくう）、材料が数個転がる木箱、台の端にプリズム。
- **奥（画面上 2/3）**: 工房の中と、窓の外の港。
  - 工房の壁: 点火用の配線。一箇所が切れて火花を出し、その先の作業灯が消えている。（銅）
  - 窓の外の沖: 小さな船。人が腕を振っている。暗い。工房の桟橋に信号炎の発射台。（ストロンチウム）
  - 作業机: 点火用リモコン装置。電池室が空でランプが消えている。隣に小さな電池工場の受け口（材料を入れると電池が出てくる装置）。（リチウム）

縦画面: 上下に積む。横画面: 左に台、右に工房と港を並べる。どちらも同じ世界オブジェクトの再配置であり、別実装にしない。

### 3.2 材料（v1）

| 元素 | 台に転がる材料 | 炎色 | 主な発光線 |
|---|---|---|---|
| 銅 | 銅くず線の束 | 青緑 | 510.6 / 515.3 / 521.8 nm（緑）、他に青の線群 |
| ストロンチウム | 赤い信号炎の薬剤粒（灰白色の顆粒） | 緋（明るい赤） | 460.7 nm（青）、606 nm 付近（橙）、650–690 nm 帯（赤） |
| リチウム | 電池材料の粉（白い塩）の小壺 | 深紅 | 670.8 nm（赤・強）、610.4 nm（橙・弱） |

材料の見た目は v1 では「炎色と無関係な地味な見た目」に留め、鉱物の再現（v2）は行わない。
バーナーの素の炎は青（ガス炎）。何も入れないと青いままで、これも現実通り。

### 3.3 ループ

1. 世界のどこかが困っている（常に1〜2箇所）。
2. 子どもが材料を指で押さえ、炎へ引きずる。炎に触れている間だけ炎全体がその元素の色になる。
3. 指を離さずに運ぶ。材料は炎から出た後も約3秒、その色で余熱発光する（**許容した乖離**。運搬中に色を見せるため）。
4. 困っている場所へ落とす。
   - 合っていれば仕事が動き、世界が変わり、そこにいる人が「銅、ありがとう」と言う。
   - 違っていれば仕事は動かない。線に置いても火花は止まらず電気は流れない。材料はその場に残り、拾い直せる。
5. 数十秒後に別の困りが起きる。

名前が聞こえる瞬間は2つだけ。困りが起きたとき、そこにいる人が手を振って「どう〜！」「ストロンチウム〜！」「リチウム〜！」と呼ぶ。届いたとき「銅、ありがとう」。それ以外に名前は出ない。

### 3.4 三つの仕事（すべて別の現象）

- **銅**: 切れた配線の隙間に銅線を置く → 火花が止まり、線がつながり、電流が走って作業灯が灯り、工房の奥が明るくなる。
- **ストロンチウム**: 桟橋の発射台に薬剤を入れる → 発射台が赤い信号炎を打ち上げ、沖が赤く照らされ、船の人が腕を下ろし、救助船の光が近づく。
- **リチウム**: 電池工場の受け口に粉を入れる → 装置が動き、電池が出てくる。電池はそのまま滑ってリモコンの電池室に入り、ランプが点き、花火の点火テストでパチッと小さな火が飛ぶ。

### 3.5 プリズム

台の端に三角プリズム。指で炎の前まで引きずると、炎の後ろの壁に縞が投影される。
縞は表 3.2 の発光線を波長軸上に描く。リチウムは赤の太い一本、ストロンチウムは赤帯＋橙＋青の複数、銅は緑の複数。
プリズムを離すと台に戻る。プリズムが仕事に関係する必然は作らない（見分けの道具、発見の道具として置く）。
v1 では「二つの赤が縞では違う」を子どもが偶然見つけられる配置にするだけで、誘導はしない。

### 3.6 音

- 名前: Web Speech API, `lang=ja-JP`。読みはかな指定（銅→「どう」）。iOS では最初のタッチ後にしか鳴らせないため、初回ドラッグ開始で無音の発話を一度行って解錠する。
- 環境音: バーナーの「シュー」、材料が炎に入る「ジュッ」、火花、波。ファイルを持たず Web Audio で合成する（配布物を小さく保つ）。
- 合成音声が利用不可の端末では無音で動作し、名前無しでも遊べることを保証する（名前は追加の情報であり、成立条件にしない）。

## 4. 技術構成

| 層 | 選択 | 理由 |
|---|---|---|
| 言語 | TypeScript | 型による仕様の固定 |
| ビルド | Vite | PWA プラグイン、開発サーバ、静的出力 |
| 描画 | PixiJS v8（WebGL）＋ 炎はカスタム GLSL フィルタ | 2D 配置・ドラッグ・レイヤを任せ、炎だけシェーダで書く |
| 炎シェーダ | ノイズ系手続き炎。色は発光線から CIE 1931 → sRGB へ変換して算出。青いガス炎を基底に元素色を重ねる | 「本物の色」の保証 |
| 音声 | Web Speech API / Web Audio API | 追加ファイル不要 |
| 単体テスト | Vitest | ルール・色算出・状態遷移の高速検査 |
| 操作・画面検証 | Playwright（Chromium 同梱。iPhone/iPad の viewport とタッチをエミュレート） | 本来の入力経路で検証、スクリーンショット取得 |
| 配信 | GitHub Pages（`main` の `dist`） | 追加インフラ無し |

ゲーム時間は `GameClock` を通す。描画のノイズ時間もこの時計から取る（壁時計は使わない）。

## 5. 局所再現・観測・再検証の仕組み（受け入れ条件）

ユーザー提示の開発要件を、以下の「薄い入口」で満たす。専用フレームワーク・巨大シリアライザ・独自テスト言語・MCP サーバは作らない。

### 5.1 入口

開発ビルド（`import.meta.env.DEV` または `?dev=1` を持つ dev サーバ）でのみ `window.__fire` を公開する。本番ビルドには含めない（tree-shaking で除去されることをビルド後の grep で確認する）。

```
__fire.loadScenario(name)      // 名前付きシナリオを通常の初期化経路で読み込む。Promise<void>（操作可能になった時点で解決）
__fire.ready()                 // 現在の準備状態: 'loading' | 'ready' | 'busy'
__fire.state()                 // 副作用なし。小さな JSON（下記）
__fire.log(n?)                 // 直近 n 件の出来事ログ（順序付き）
__fire.clock.mode('manual'|'real')
__fire.clock.step(ms)          // 本番と同じ update を刻みで進める。処理を飛ばさない
__fire.rng.seed(n)             // シナリオが既定 seed を持つ。上書き可
__fire.speech.captured()       // TTS を dev では実発話せず、発話予定テキストを記録する
__fire.dump(section)           // 必要時のみ詳細（例: 'materials' | 'jobs' | 'flame'）
```

### 5.2 state() の項目（仕様から選ぶ）

```
phase            'idle' | 'dragging' | 'delivering' | 'job_running'
held             { id, element, inFlame, afterglowMs } | null
flame            { element | null, intensityPct }
jobs             [{ id, element, status: 'waiting'|'called'|'done'|'cooldown', calledAt }]
materials        [{ id, element, at: 'bench'|'held'|'site:<jobId>' }]
prism            { at: 'bench'|'held', projecting: element | null }
input            { accepting: bool, rejectReason?: string }
waitingFor       string | null   // 例: 'job_animation', 'next_trouble_timer'
```

### 5.3 ログ

固定長リングバッファ（既定 200 件）。項目: 入力（down/move/up の要点のみ）、状態遷移、材料が炎に入った／出た、届け先判定と結果（成功／不一致の理由）、発話テキスト。毎フレームの位置ログは出さない。

### 5.4 名前付きシナリオ（v1）

| 名前 | 開始状態 |
|---|---|
| `bench_idle` | 全材料が台、困りなし、炎は青 |
| `copper_called` | 配線が切れて火花、作業員が「どう〜」を呼んだ直後 |
| `flare_called` | 沖の船が手を振り、桟橋の人が「ストロンチウム〜」を呼んだ直後 |
| `battery_called` | リモコンの電池室が空、机の人が「リチウム〜」を呼んだ直後 |
| `two_reds_on_bench` | 困りなし、ストロンチウムとリチウムの材料が台の中央に並ぶ。プリズム検証用 |
| `wrong_delivery` | `copper_called` と同じだが、手にリチウムを持って配線の上にいる状態の直前 |

各シナリオは「通常の初期化 → 世界生成 → 指定状態へ進める」の順で作り、前回の残りを持ち越さない（loadScenario は必ず全破棄から始める）。

### 5.5 再現に影響する要素と固定方法

| 要素 | 固定 |
|---|---|
| 初期状態 | シナリオ名 |
| 乱数 | シナリオ既定 seed（困りの発生順、火花の散り方） |
| 入力列とタイミング | Playwright の実ポインタ操作＋ manual clock で `step` を挟む |
| 時間進行 | manual clock。`step(16)` を基本刻みとする |
| 保存データ | 無し（保存機能なし） |
| 描画ノイズ | GameClock 由来なので同一 |
| TTS | dev では記録のみ。実発話は再現対象外と明記 |

ピクセル完全一致は要求しない。スクリーンショット比較は「炎領域の平均色相が仕様範囲内」など仕様に基づく許容差で判定する。

### 5.6 最初に実証する1場面

`copper_called` で以下を通す。

1. `loadScenario('copper_called')` → `ready()==='ready'`
2. `state()` で `jobs[copper].status==='called'` を確認
3. Playwright の実タッチで銅線を押さえ、炎へ移動 → `state().flame.element==='copper'`、スクリーンショットで炎領域が青緑
4. そのまま配線の隙間へ移動して離す → `jobs[copper].status==='job_running'` → `clock.step` で進めて `'done'`、作業灯の領域が明るくなる
5. `log()` に 入力→炎入り→炎出→届け→成功→発話「銅、ありがとう」 の順が残る
6. `loadScenario('copper_called')` を再実行し、同じ入力列で同じ結果

これが通るまで他の場面を作らない。

## 7. リスクと対応

- **絵の質**: 実写も絵師も無い。工房・港は PixiJS の図形＋グラデーション＋光で描く。写実は炎と光に集中させ、他は簡潔な形にする。子どもは炎を見るので許容と判断。
- **iOS の音声制約**: ユーザー操作後にしか鳴らない。最初のドラッグで解錠。声質は端末依存。
- **銅の見た目と炎色の不一致**: 銅線は茶色、炎は青緑。これは現実であり、試行で学ぶ設計とする。切れた配線の周辺に緑青（青緑）を置き、現実に基づく手がかりにする。
- **余熱発光**: 現実には消える。運搬中に色を見せるための意図的な乖離。ユーザー承認済みの「ある程度の乖離」に含める。
- **WebGL 性能**: 炎は一箇所、解像度を落とした FBO に描いて拡大する。
- **本番への dev 入口の漏れ**: ビルド後に `__fire` が bundle に無いことを検査に含める。

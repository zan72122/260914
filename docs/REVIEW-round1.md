# 炎色反応ゲーム — 4歳児インタラクション・レビュー

**レビュー方法**: `localStorage` を空にした状態（`__game.resetProgress()` → reload）から、`__game.goto` を使わずに炉の見た目だけを頼りに5元素すべてを1周し、その後に分光器フローを実行。
座標の取得にのみ `hitPoints()` を使用（何をすべきかのヒントには使っていない）。

**実機エミュレーション**: iPhone 15 縦 393×852 dpr3 / iPad 横 1180×820 dpr2 / iPhone 15 横 852×393 dpr3、すべて `hasTouch, isMobile`、タッチは CDP `Input.dispatchTouchEvent`（`tests/helpers/gestures.mjs` を import）。

**スクリーンショット**: `shots/<device>/`。
- `shots/iphone15-portrait/` … 本編1周（enter 14枚 / change 26枚 / return 14枚、実測間隔 ≈0.58s。`page.screenshot` 1枚に ≈330ms かかるため、指示の250ms は達成できていない）
- `shots/iphone15-portrait-run1/` … 同じ手順の1周目（`run1/xxx.png` と表記したファイルはこちら）
- `shots/iphone15-portrait-fast/` … 実測間隔 ≈0.28s のリチウム連番（黒フレーム検証用）
- `shots/iphone15-portrait-spectro/`, `shots/ipad-landscape-spectro/` … 分光器
- `shots/ipad-landscape/`, `shots/iphone15-landscape/`, `shots/probe/`, `shots/barium-climax/`
- ログ: `run-portrait.txt`（phase/voice の 100ms サンプリング付き）、`run-timing.txt`（スクショ無しの実測時間）、`log-probe.txt`

**注意（計測の性質）**: スクショを撮りながらのフレームは 1 枚 ≈330ms を消費し、`dt` クランプ（1/20s）のせいでゲーム内時間そのものが遅くなる。したがって所要時間は **スクショ無しの `run-timing.txt` を正**とし、連番はタイミングではなく**絵の連続性の証拠**として扱った。

## 設問への回答

### 1. 4歳児が説明なしで最初の操作を始められるか — **△（始められるが、最初の一手は空振りする）**

最初の3秒に目に入るもの（`shots/iphone15-portrait/000〜012-hearth-first3s-*.png`）:
1. **呼吸する大きな炎**（画面中央上、唯一の光源、明らかに一番目立つ）
2. その右にヒノコ（直径 ≈50px、目は黒い点2つ）
3. 下部に空の棚（暗い穴5つ）
4. 最下部に試料皿5つ（`dish:*` r=33、y=648〜682）— 3秒時点でリチウム皿がわずかに浮いて光る

**問題 A（高）— 炎をタップしても完全に無反応。**
`shots/probe/000-after-flame-taps.png` と `log-probe.txt`: 炎の中心を3回タップしても `state` は `phase:"idle"` のまま、視覚フィードバックもゼロ。ヒノコ・棚も同様に無反応。炉で反応するのは**試料皿とミュートアイコンだけ**（`src/scenes/hearth.js:405-430` — `onTap` はミュートのみ、`onDrag` の hitTest は分光器と皿のみ）。しかも `hitPoints()` は `flame` を返すので、QA 上は「触る対象」に見えるのに実装は無視する。
4歳児の最初の指は、間違いなく「一番大きくて動いていて光っているもの」＝炎に行く。そこで**何も起きない**のは、ゼロ説明設計の最初の穴。
**修正案（最小）**: `hearth.js` の `installGestures()` に炎ヒットの `onTap` を追加し、(a) 火の粉を散らす、(b) `targetDish` の皿を大きく wobble させる、(c) `idleT = IDLE_WIRE_AFTER` にしてワイヤーループを即座に皿へ降ろす。＝「炎を触ったら、炎が皿を指した」に変換する。

**問題 B（中）— ヒノコの視線が読めない。**
誘導の主役が「視線」なのに、iPhone 縦でヒノコの目は直径 ≈6px の黒点で、瞳のオフセットは数px（`004-hearth-first3s-f04.png`）。iPad（`shots/ipad-landscape/013-*.png`）でようやく向きが分かる程度。連番を並べても視線の往復は読み取れない。
**修正案**: `hearth.js` の顔描画で瞳を 1.6 倍・白目を追加し、視線移動時に**顔（体）ごと 8〜10° 傾ける**。手（既にある2つの丸）を対象側に寄せる。

**問題 C（中）— ワイヤーループの誘導が遅く、かつ「棒」に見える。**
`IDLE_WIRE_AFTER = 8.0`（`hearth.js:33`）。8秒は4歳児には長い。降りてきた絵（`012-hearth-first3s-f12.png`）は、細い灰色の直線が画面を縦断し先端に白いリングが付いた状態で、「乗せる穴」より「棒」に見える。
**修正案**: 4.0s に短縮。ワイヤーを線ではなく「垂れ下がるロープ＋白熱したリング」にし、リングだけを皿の色で明滅させる。

**問題 D（低〜中）— 皿が小さく暗い。** iPhone 縦で皿 r=33、中身 ≈24px、縁の色が背景と同系。当たり判定は 1.6 倍で十分寛容だが、**見つけにくい**。ターゲット皿以外にも弱いリムライトが欲しい。

### 2. 元素名を知らなくても遊べるか — **○（4/5は第1フレームで分かる）**

文字・矢印は全ワールドでゼロ（`fillText` を使っていないことはコード上も確認）。第1フレームの読みやすさ:

- **リチウム**（`028-lithium-world-first.png`, iPad `028-*`）: **最良**。浮いている赤いカプセルと、車体の赤く縁取られたカプセル型の穴が**同じ形**。ローバーの首も穴を向く。説明不要。
- **銅**（`085-copper-world-first.png`）: 切れた線の両端が白く光り、点線ガイドが息をする。左端にくねった銅線のかけら。「つなぐ」は読める。
- **ナトリウム**（`142-sodium-world-first.png`）: 皿の上の大きなじゃがいも＋浮かぶ白い角砂糖状の粒。「かける」は読める。ただし**湯気が無く**、じゃがいもがただのベージュの塊に見える（設計 §2.3 は湯気つきを要求）。
- **ストロンチウム**（`199-strontium-world-first.png`, iPad `199-*`）: 筒の口が**星形の穴**、上に星のタネ。装填までは自明。
- **バリウム**（`256-barium-world-first.png`）: **ここだけ第1フレームで分からない**。板は既に台の上に寝ており、「円を描く」というアフォーダンスは溝を回る光とヒノコの自転だけ。静止画では読めない。

**問題 E（中）— バリウムの「回す」が伝わらない／偶然クリアできてしまう。**
`log-probe.txt`: バリウム世界で**円運動ではない雑なタップを8回**しただけで `turns01=0.55`、続けて短いスワイプ6回で `phase=complete`。寛容さは設計通りだが、**指の回転と世界の変化の因果が結ばれないまま終わる**恐れがある。
**修正案**: `src/worlds/barium.js` — (a) 起動直後に板1枚だけを溝へ**自動でひと回し**して見本を見せる（0.8s、以後は子ども次第）、(b) 指が触れている間、指と台中心を結ぶ光の腕を描いて回転入力を可視化する。

**問題 F（中）— ストロンチウムの「長押し」の誘導が弱い。** 装填後の誘いは筒の震えのみ。`210-strontium-change-f09.png` のように押し始めれば光の水位が上がって分かりやすいが、**押し始めるまで**の手掛かりが無い。
**修正案**: `src/worlds/strontium.js` — 装填直後に筒の光の水位を 0→30%→0 と一度だけデモ（0.6s）。

### 3. 遊んだ後に元素名が音として残るか — **◎（実装は完璧）**

上表のとおり、5元素すべてで**視覚的最高潮と同フレーム（±0.1s以内）に1回だけ**発火。ストロンチウムで3発撃っても2発目以降は鳴らない（`spoken` フラグ、`strontium.js:288`）。ナトリウム前半の塩では鳴らない。
唯一の注意点は設計どおりの `speechSynthesis` 依存で、日本語音声が無い端末では3音モチーフのみになること（仕様内）。**ここは直す所が無い。**

### 4. 紙芝居ではなく、自分で世界を変えた感覚があるか — **△**

因果は明確（`092-copper-change-f05.png`: 指の軌跡に沿って銅線が伸びる／`210-strontium-change-f09.png`: 押している間だけ光の水位が上がる）。変化の規模も十分（`run1/065-copper-return-f04.png` の街全体点灯、`shots/barium-climax/clim-00.png` の大俯瞰、`216-strontium-change-f15.png` の大輪）。
一方で「勝手に進む」箇所が複数ある。

**問題 G（中〜高）— リチウムと銅は「1操作＋4.5秒の見物」で自動終了。**
`lithium.js:383` `doneT >= 4.6` → `leaving`、`copper.js:513` `flow >= 4.4` → `leaving`。操作は**生涯1回だけ**で、以後 `hitPoints()` は空を返す（`copper.js:1076`）。実測滞在 11.0s / 10.3s（設計は30〜60s）。
4歳児がやっと「自分がやった」と気づいた瞬間に、世界は勝手に縮んで棚に入る。
**修正案（最小）**: 帰還までを 4.5s → 9〜10s に延ばし、その間だけ**追加の小さな操作**を許す。リチウム＝走るローバーをタップすると加速して砂煙が増える、銅＝消えたままの窓を1〜2枚残しておきタップで点く。「もう一回触れる」だけで紙芝居感は大きく減る。

**問題 H（低）— 自動進行の連鎖。** ナトリウム: 塩3回で自動的に街へティルト上昇（`sodium.js:262`）、街灯3本で残り2本が自動点灯（`CHAIN_AFTER=3`）。銅: 到達率50%で自動完走。いずれも「待たせない」ための設計通りだが、ナトリウムは**2回の自動進行が連続**するため受け身に感じやすい。せめて街灯は4本目まで手で点けさせてよい。

### 5. もう一度炎へ試料を入れたくなるか — **△**

帰還後の炉は正しく作られている: 棚にミニジオラマが増え（`run1/044-lithium-hearth-after.png` → `241-strontium-hearth-after.png` → `298-barium-hearth-after.png` で1〜5個に増えるのが見える）、まだ遊んでいない皿が光って揺れ、ヒノコは両手を上げて跳ねる（`051-lithium-change-f21.png`）。**構造は設計どおり。**

**問題 I（中〜高）— ミニジオラマが「自分の世界」に見えない。**
iPhone 縦で直径 ≈68px、中身が抽象的すぎる。特に**リチウムはローバーが描かれていない**: `hearth.js:62-69` の実装は「赤い角丸長方形＋光の玉が横に流れる」だけで、車輪も車体も無い（`run1/044-lithium-hearth-after.png`、分光器画面の `shots/ipad-landscape-spectro/004-lithium-spectro-view2.png` でも同じ赤いカプセルが出る）。銅も「窓5つが点滅」で電車が無い。
設計 §3.3 の決定打「この線の並び＝この世界」は、**リチウムだけ絵が世界と一致していない**（線の下に出るのは走るローバーではなく、炉で見たかけらと同じ赤いカプセル）。
**修正案**: `drawDiorama()` の `case 'lithium'` を、車体＋車輪3つ＋前方への光の帯の**シルエット**が横切る絵に置換（20行程度）。`case 'copper'` に小さな電車を1両追加。

**問題 K（低）— ミニジオラマが棚板から左にはみ出す。** `run1/044-lithium-hearth-after.png`、`run1/098-sodium-return-f06.png`: 円が棚板の左端をはみ出し、右側には使われていない穴が残る。円の直径が穴のピッチより大きく、原点も合っていない（`hearth.js:218-235` 付近）。

### 6. 画面遷移がカットなしで連続しているか — **○（ただし2つの汚れ）**

黒フレーム・唐突な切り替えは**ゼロ**（全フレーム輝度計測済み）。炉→ワールドは「炎が色づく→画面いっぱいに色が溢れる→粒が凝集→世界が背景から立ち上がる」が連続（`020〜026-lithium-enter-f06〜f12.png`）。ワールド→炉は「世界が円の中に縮んで棚の穴に着地する」（`047-lithium-change-f17.png` → `051-...-f21.png`、`run1/096-sodium-return-f04.png`）。

**問題 M（中〜高）— ストロンチウム帰還時、花火が太い実体の棒として描画される。**
`227-strontium-return-f00.png`（および run1 の `128/129-strontium-return-f05/f06.png`）: 炉の上に、角の丸い**太いピンクの長方形が10本、放射状に**重なる。減衰も尾も垂れも無く、明らかに壊れた絵。世界の中での花火（`216-strontium-change-f15.png`）は極めて美しいので、これは**帰還オーバーラップ中だけの描画バグ**。`strontium.js:1006 drawBurst()` の `lineWidth = b.R * 0.05` はワールド単位で、退出時のカメラ寄り（`FRAME.out` / `frameTo`）でスケールが跳ね上がると太くなるのが原因と思われる。
**修正案**: `drawBurst()` の 2 本のストローク幅をカメラスケールで割ってスクリーン空間固定にする。即応の代替として `leaving === true` の間は `bursts` を描かない（火の粉パーティクルだけ残す）。

**問題 L（中）— 遷移中に画面が単色で飽和する時間が 0.6〜1.2s ある。**
`run1/094-sodium-return-f02.png`（黄一色、mean=128）、`run1/039-lithium-return-f09.png`（赤一色）、`285-barium-return-f01.png`（緑一色）。炉も世界もほぼ見えない。カットではないが、4歳児には「消えた」に見えかねず、単純に眩しい。
**修正案**: `scene.js` の連続遷移で `applyAmbient` のピーク alpha を下げる（現状の flood を 0.75 倍程度に）／飽和のピーク時間を 0.4s に短縮。

### 7. 縦横どちらでも操作対象が親指の届く範囲・セーフエリア内にあるか — **○（1箇所だけ例外）**

全デバイスで全 `hitPoints()` がビューポート内、端から十分内側（`engine.clampSafe` を全シーンが通している）。

| デバイス | 皿の位置 | 画面下端からの割合 |
|---|---|---|
| iPhone 縦 393×852 | y=648〜682 | 下から 20〜24% |
| iPad 横 1180×820 | y=611〜648 | 下から 21〜25% |
| iPhone 横 852×393 | y=293〜310 | 下から 21〜25% |

ワールド側も良好: リチウムのかけら/スロットは縦で y=480/579、iPhone 横で y=145/250、いずれも thumbZone 内。バリウムの中心 y=452（縦）。ストロンチウムの筒 y=549（縦）。

**問題 N（中）— ナトリウム後半の街灯が親指帯の外。**
`150-sodium-change-f06.png`: 灯具（光る傘＝目が行く場所）が y≈100/852 = **上から12%**。柱の当たり判定は下まで伸びるが、**光る所を押したい**のが子どもの自然な行動で、そこは片手持ちでは届かない。
**修正案**: `src/worlds/sodium.js` のティルト到達位置を下げ、灯具列を y≈0.30〜0.40H に置く（柱は下に伸ばす）。または柱の根元にも点灯前の明滅を出して「下を押しても良い」ことを絵で示す。

**問題 O（低〜中）— 分光器が左端に出る。** iPhone 縦 x=61（左端から61px）。右利きの親指からは最も遠い隅。iPad 横では x=354 で問題なし。縦では炉の**右側**（皿の弧の外側）に置いた方が届く。

**問題 P（低・要実機）** ミュートアイコン (364,29) はヘッドレスでは inset=0 のため検証不能。ダイナミックアイランド直下なので実機確認が必要。

### 8. 「赤＝リチウム」と誤学習されない設計になっているか — **○（三層とも実装されている）／ただし第3層に到達できない**

- **第1層（形）**: 皿の中身は「ガラス蓋つきの銀の小石」vs「赤い針の束」で明確に別物（`shots/ipad-landscape/013-hearth-after-9s-idle.png` で一目瞭然）。
- **第2層（世界）**: 「砂丘で動き出すローバー（ドラッグで挿す・追従パン）」vs「夜の河原で打ち上がる花火（溜めて離す・見上げ＋シェイク）」。共通点は色だけ。**ここは非常に強い。**
- **第3層（分光器）**: `009-strontium-spectro-view2.png` が決定的に良い。上段（暗い記憶）＝リチウムの2本すっきり、下段（明るい）＝ストロンチウムの**青1本＋赤4本のにぎやか**。文字ゼロで「違う子だ」が分かる。棚のミニも「赤い点」vs「赤い放射星」で別物（`241-strontium-hearth-after.png`）。

**問題 R（高）— 分光器を掴める時間が事実上3秒しかなく、それ以前の接触は完全に無視される。**
`hearth.js:480` `spectroGrabbable()` は `phase === 'idle' | 'hold' | 'carry'` のみ true。炎に投入した直後は `phase === 'reveal'` なので**掴めない**。`hold` に入るのは `revealT >= 0.75`（=試料が着火してから0.75s）で、`HOLD_SECONDS = 3.0`（`hearth.js:30`）で終わる。さらに炎への投入判定は `onMove`/`onEnd` の両方で `phase === 'hold'` を要求（`hearth.js:436, 456`）。
実測（`log-spectro-*`, 1回目）: 皿タップの **+0.9s** に分光器へ指を下ろすと**何も起きず**、そのままリチウム世界へ突入。**+1.8s** に下ろした2回目は成功。
4歳児に「1.5秒待ってから3秒以内に拾って炎まで運べ」は不可能に近い。三層目は**設計上は存在するが、実際にはほぼ見られない**。
**修正案（最小）**: (a) `spectroGrabbable()` に `'reveal'` を追加し、(b) 分光器が握られている間は `phase` を `hold` に固定して `holdT` を進めない（＝持っている限り炎は色づいたまま待つ）、(c) 離したら `hold` を再開。これで「拾えた＝必ず覗ける」になる。

**問題 S（中）— 分光器アンロック後、毎回3秒間じっと待たされる。**
`run-portrait.txt` vlog: バリウム入場時に `hold`(t=161858) → `reveal`(t=164890) と**3.0秒の空白**が入る。分光器を使わない子は、以後すべての着火で毎回3秒待たされる。
**修正案**: `hold` 中に指が画面に触れていなければ 1.2s で切り上げる（触れた瞬間に 3.0s へ延長）。

**問題 Q（中）— リチウムのスペクトルが「すっきり1本」に見えにくい。** `004-lithium-spectro-view2.png`: 610nm のオレンジ線が赤とほぼ同じ太さ・明るさで描かれ、「1本＋細い添え物」ではなく「2本」に見える。`spectroscope.js` の `FAT` と強度 `i=0.35` の反映が弱い。線幅を強度の 1 乗以上で効かせて 0.35 倍の細さにするだけで対比が立つ。

### 9. 科学的誤解を招く絵がないか — **○（ほぼ問題なし）**

- **リチウム＝電池変身**: 描かれていない。かけらは抽象的な赤いカプセル、スロットは電池セル型のケース、赤は**配線を走る光**として継承（`run1/033-lithium-return-f03.png` で車体の赤い配線が見える）。金属リチウムはガラス蓋の皿の中だけ。**設計 §2.1 の規則を守れている。**
- **ナトリウム金属＝食塩**: 守れている。塩は最初から白い立方体で、光っても**立方体のまま**街灯に入る（`150-sodium-change-f06.png`）。銀色の金属は食卓に一切出ない。前半と後半は因果ではなく「移動」として演出されている。
- **銅**: 繋がった後、線は銅色（オレンジ）に落ち着き、流れる光だけが青緑（`run1/065-copper-return-f04.png`）。素材と電気の分離ができている。**5元素中もっとも正確。**
- **ストロンチウム／バリウム**: 火薬・導火線・着火動作は一切無い。抽象化された「星のタネ」「光の板」。

**問題 T（低）— 打ち上げ筒が乾電池に見える。** `199-strontium-world-first.png`: 灰色の円筒＋横帯2本＋発光部で、単三電池のシルエットに近い。リチウム世界が「電池スロット」なので、**赤い2元素の間に「電池」という余計な共通項**ができてしまう。筒を上すぼまりの木台付き／地面に半分刺さった形にして、円筒感を消したい。

**問題 V（低）— じゃがいもに湯気が無い。** 設計 §2.3 の「茹でたて（湯気つき）」が未実装で、食べ物としての読みが弱い（`142-sodium-world-first.png`）。湯気は「塩をかけたくなる」動機そのものなので、2〜3本の白い揺れる帯を足す価値がある。
